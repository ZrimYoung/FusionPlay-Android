# 小米盒子原生投屏切换

当前方案为可恢复的临时切换。尚未解决同一 IP 上两套接收器同时运行时，手机把妙播状态和歌曲信息发给原生视频接收器的问题。

## 新版：一次授权的系统模式开关（1.2.4-native-mode / 10212）

本版优先使用小米原生组件的 `touping_square_mode` 配置和包定向的 `SQUARE_MODE_CHANGE` 广播。原生组件自行暂停、恢复 MiPlay/音乐接收等服务，不修改包的 enabled 状态。仅适用于已核查的原生组件；其他固件仍须单独验证。

1. 安装新版后，通过电脑对实际安装包授予一次权限。当前修复包命令：
   `adb shell pm grant com.fusionplay.android.portfix android.permission.WRITE_SECURE_SETTINGS`
2. 重新打开 FusionPlay，在设置中开启“暂停原生投屏”。
3. 保持 App 在前台，手机重新选择接收器。
4. 关闭开关、点击“恢复原生投屏”或离开 App 时，恢复先前配置。

`WRITE_SECURE_SETTINGS` 可修改系统安全设置，并非普通“允许修改系统设置”。本实现只写投屏模式键，通知目标限定为 `com.xiaomi.hyper_connect.tv`。如需撤销权限，应先恢复原生投屏，再执行 `pm revoke`；不要在暂停期间卸载或清除 App 数据，否则可能丢失原配置恢复记录。

未完成该权限授权时保留原 Shizuku 备用路径。系统模式控制服务运行在普通 App 的独立 `:native_cast_settings` 进程，不由 ADB 或 Shizuku 启动。关闭调试后的开关与 USB 播放已通过本机实播验收；盒子重启后的权限保留仍待验证。

## 恢复机制与边界

修改前同步保存原值，包含原设置不存在的情况；保存失败不修改系统。发现系统已有暂停模式时拒绝接管。通知或恢复失败保留恢复记录，支持重试。

前台每五秒续约；离开前台一秒后请求恢复。独立控制进程监听主进程 Binder 死亡，超过十五秒未续约也尝试恢复。App 重新打开、收到开机完成或自身更新广播时检查未完成的恢复记录。恢复前遇到其他来源的配置变化时不强行覆盖。

整个 App 被系统“强行停止”会同时终止控制进程，无法保证立刻恢复；重新打开 App 后检查恢复记录。自动恢复也受系统进程管理和开机广播是否送达影响，不能承诺所有故障下都即时恢复。

备用 Shizuku 路径保持原有短租约、进程检查和固定包停止/启动行为。它仍依赖 Shizuku 存活，不代表已解决该固件的 USB 与调试冲突。

## 验证

本次构建的 Android 单元测试 30 项通过，其中新增系统模式测试 7 项，覆盖原值/缺失值恢复、拒绝外部模式、记录写入失败、进程重建、通知失败重试、授权失效及续约超时。Flutter 设置页 8 项测试通过，静态检查通过。

上次原生机制验证确认暂停时 8899 关闭，恢复后重新开放，原生进程保持存活。2026-10-25 集成实测：在 MiTV-AZFU0 上安装 10212 并授予权限，全程未运行 Shizuku。App 暂停后原生 8899 关闭，FusionPlay 46655 保持开放；超过租约时限后前台续约仍正常。恢复按钮及返回桌面均恢复原本不存在的设置并重新开放 8899，原生进程始终存活。强杀主进程后原生服务恢复；整个 App 强行停止时设置仍为 1，重新打开后恢复记录生效，两个端口重新开放。App 重启后授权仍有效。

2026-10-25 的集成测试保持 ADB 开启。2026-10-26 用户同意后关闭 ADB，约33秒外部检查显示调试端口关闭、FusionPlay 接收端口保持开放、原生端口保持关闭；无 Shizuku 运行。用户随后按提示关闭再开启暂停开关并投送歌曲，回复“都正常”：确认开关无报错、歌名封面更新、手机不转圈及 Redmi USB 音箱出声。至此本轮 ADB 关闭后的使用流程通过用户实播验收。盒子重启后的授权/恢复及长期稳定性仍未验证。端口恢复不等于所有原生投屏协议均已验收。

## 构建

```sh
cd flutter
flutter build apk --profile --target-platform android-arm \
  --build-name=1.2.4-native-mode --build-number=10212 \
  --dart-define=FUSIONPLAY_VERSION=1.2.4-native-mode
```

使用 profile APK 避开此盒子上 debug 模式曾出现的 Flutter 无响应。

## 后续同步与键盘修复（1.2.4-sync-keyboard / 10210）

持续时序日志显示，旧版的 Android 输出延迟从启动时估计的 8ms 收敛到实测约 35ms 后，已经开始的播放没有重新对齐，留下约 27ms 的固定排程落后。本版先等待两次稳定的硬件测量，再建立首次对齐；第一个实测值直接替换启动估值，后续临时取不到时间戳时保留已有实测值。等待上限一秒，避免无时间戳设备一直静音。此改动不涵盖电视接收 HDMI 后的音效、缓冲等声学延迟，仍需全屋实播复核。

此盒子的输入法服务按文本编辑控件标记决定是否启动搜狗输入法，而当前 FlutterView 没有实现该声明。名称编辑改用 Android 原生 EditText 对话框，实机已确认搜狗键盘可见。取消不会修改草稿，完成只回填草稿，仍需在设置中选择“应用”才保存名称。

33 项音频同步测试、7 项遥控器设置测试通过，Flutter 静态检查通过，ARM32 profile APK 构建安装成功。

## 输出链路校准（1.2.4-audiosync / 10211）

上述首次校准经实播日志验证，稳定排程误差已降至约0.02–0.08ms且没有断供，但用户仍能听到固定落后。连接的 HDMI 接收端没有提供有效音频延迟声明，因此内部时间戳无法直接测得完整出声延迟。

设置新增“声音同步校准”，范围0–500ms，每次增加或减少10ms，可归零。盒子声音落后时增加提前量。值保存在 Android 本地设置，重新启动后保留；更换输出设备后应重新校准。

调整实时作用于妙播输出。旧时序先淡出至零，在静音边界重新对齐后淡入，平稳播放继续使用原采样速率。补偿同时计入排程和总延迟反馈。此设置只影响 FusionPlay 妙播，不修改电视和原生投屏的系统音频设置。默认值0，实际补偿量需要通过听感或声学录音校准，不能把试验值当作测量结果。

35项音频测试与8项设置测试通过，Flutter静态检查通过。

本机实播对照：设置提前100ms后，用户先确认“更接近同步”，随后确认“已经基本同步，可以接受”。已保留该值并验证 App 重启后仍在。这是当前盒子与 HDMI 接收端组合的听感校准结果，不是声学仪器测量值，也不应作为其他设备或 USB 音箱的默认补偿。
